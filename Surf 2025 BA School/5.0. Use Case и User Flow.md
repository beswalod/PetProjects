# 5.0. Сценарии использования и навигация

## 1. Use Case: «Студент подаёт заявку в администрацию и отслеживает статус»

### 1.1. Паспорт Use Case
- **UC-ID:** UC-ADM-01
- **Основной актор:** Студент
- **Вторичные акторы:** Сотрудник администрации, Сервис уведомлений
- **Цель:** Получить решение по организационному вопросу без очного визита
- **Предусловия:**
  - Пользователь авторизован
  - Профиль студента активен
  - Справочник категорий заявок загружен
- **Триггер:** У студента возник запрос (например, справка, академический отпуск, пропуск)
- **Постусловие (успех):**
  - Заявка имеет финальный статус (`completed` или `rejected`)
  - Студент получил уведомление о результате

### 1.2. Основной успешный сценарий
1. Студент открывает раздел «Заявки».
2. Система показывает список ранее созданных заявок и кнопку «Новая заявка».
3. Студент нажимает «Новая заявка».
4. Система открывает форму: категория, тема, описание, вложения.
5. Студент заполняет форму и отправляет заявку.
6. Система валидирует данные и создаёт запись со статусом `submitted`.
7. Сотрудник администрации получает новую заявку в очереди и переводит её в `in_review`.
8. Сотрудник запрашивает доп. данные или выполняет обработку.
9. Сотрудник завершает обработку и переводит заявку в `completed` (или `rejected`).
10. Система отправляет студенту уведомление о результате.
11. Студент открывает карточку заявки, видит итоговый статус и историю изменений.

### 1.3. Альтернативные/исключительные сценарии
- **A1. Ошибка валидации на шаге 6:** система подсвечивает обязательные поля, заявка остаётся в `draft`.
- **A2. Нужны уточнения на шаге 8:** заявка переходит в `waiting_for_student`, студент получает запрос, после ответа — обратно в `in_review`.
- **A3. Студент отзывает заявку:** до начала обработки статус меняется на `closed_by_user`.
- **A4. Превышен SLA:** система эскалирует заявку ответственному сотруднику/руководителю.

---

## 2. User Flow (по шагам)

```text
Главная
  → Раздел «Заявки»
    → Список заявок
      → [CTA] «Новая заявка»
        → Форма заявки
          → Подтверждение отправки
            → Карточка заявки (статус + история)
              → (опционально) Добавить комментарий/документ
                → Обновлённый статус
                  → Закрытие кейса
```

## 3. Уточнения в ER/state по итогам сценария

### 3.1. Новые/уточнённые поля
- `Ticket.sla_deadline_at` — контроль срока обработки.
- `Ticket.closed_by` — кто закрыл заявку (студент/сотрудник/система).
- `TicketStatusHistory.comment` — причина перехода статуса.
- `TicketAttachment` (новая сущность) — хранение файлов заявки.

### 3.2. Уточнённые статусы заявки
```text
draft → submitted → in_review → waiting_for_student → in_review → completed → closed
                        └────────────────────────────→ rejected  → closed
draft → closed_by_user
```
